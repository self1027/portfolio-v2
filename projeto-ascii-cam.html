ASCII Cam — Renderização de Alto Desempenho

Processamento de Vídeo em Tempo Real com Web Workers e Zero-Copy

TypeScript Web Workers Canvas 2D Transferable Objects Image Processing Real-Time

O Problema

Processar cada frame de uma webcam (60 FPS) para converter pixels em caracteres ASCII é uma tarefa computacionalmente intensiva. Realizar este cálculo na Main Thread do browser causa o bloqueio da interface (UI Junk), resultando numa experiência travada e pouco responsiva.

O desafio era manter uma taxa de atualização estável de 30+ FPS, permitindo ajustes de brilho e contraste em tempo real, sem sacrificar a fluidez dos controlos da interface.

A Decisão: Paralelismo e Offloading

A arquitetura foi desenhada para separar a captura da renderização. A decisão principal foi mover toda a lógica matemática de conversão para um Web Worker dedicado.

Pipeline: A Main Thread captura o frame e o Worker processa a matriz de caracteres em paralelo.

Pipeline de Processamento

O fluxo de dados foi otimizado para minimizar o overhead de comunicação entre as threads, seguindo este ciclo:

  • Captura (Main Thread): O frame é extraído do elemento <video> e desenhado em um buffer temporário de Canvas para obtenção dos dados de pixel (RGBA).
  • Despacho (Zero-Copy): Os dados são enviados ao Worker via postMessage utilizando transferência de ownership, o que instantaneamente libera a memória na thread principal.
  • Transformação (Worker):
    • Cálculo de luminosidade por pixel usando a norma Rec. 709.
    • Aplicação de Brilho/Contraste via Look-Up Table (LUT).
    • Mapeamento do valor final para o índice correspondente no conjunto de caracteres ASCII.
  • Devolução: O Worker retorna uma Int32Array contendo os índices dos caracteres e outra com as cores (se o modo colorido estiver ativo).
  • Renderização (Main Thread): O sistema utiliza fillText de forma otimizada para desenhar a grid final no Canvas principal.

Otimização de Memória: Transferable Objects

Para evitar o custo de serialização (cópia de dados) entre a Main Thread e o Worker, utilizei Transferable Objects. Os ArrayBuffers contendo os dados dos pixels são "transferidos" em vez de copiados, garantindo uma latência de comunicação próxima de zero.

typescript – Comunicação Zero-Copy

// No Worker: Enviando os dados processados sem cópia
(self as any).postMessage({
    charIndices,
    colors
}, [charIndices.buffer, colors.buffer]);

Lógica de Brilho e Contraste

Em vez de calcular o contraste frame a frame para cada pixel, implementei uma LUT (Look-Up Table) dinâmica. Sempre que o utilizador altera o slider de contraste, a tabela é recalculada uma única vez, e o processamento de imagem apenas consulta o índice correspondente, poupando milhões de operações por segundo.

typescript – Processamento de Luminosidade (Rec. 709)

// Cálculo de luminância para mapeamento ASCII
const r = pixels[i];
const g = pixels[i + 1];
const b = pixels[i + 2];

// Fórmula de luminosidade percebida
let v = (r * 0.2126 + g * 0.7152 + b * 0.0722) / 255;
v *= brightness;

// Aplicação de contraste via LUT
const finalV = contrastLUT[(v * 255) | 0] / 255;

Trade-offs e Desafios

  • Compatibilidade: O uso de OffscreenCanvas (quando disponível) melhora a performance, mas requer fallbacks para browsers mais antigos.
  • Consumo de CPU: Embora a UI permaneça fluida, o processamento intensivo de matrizes consome recursos consideráveis, o que foi mitigado limitando a resolução da grid ASCII.

O que este projeto demonstra

  • Conhecimento profundo de concorrência em JavaScript (Web Workers).
  • Otimização de algoritmos para processamento de sinais e imagens.
  • Desenvolvimento de ferramentas de alta performance focadas em UX.
